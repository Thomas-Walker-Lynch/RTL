2. Endian Portability

2.1 The Endian Wars

The Little Endian model for Arabic Number Representation preserves the correlation between bit array index and the power of 2 weight of bits in a Natural Number.  Consequently for Little Endian:

```
n_LE = Sum[ 2^i,  {i, 0, extent}]
```

Here i is both the bit index into the bit array starting at the leftmost bit to be decoded, and the bit weight.

In contrast, the Big Endian model for Arabic Number Representation flips the bit weight and the bit array index.  Consequently,

```
n_BE = Sum [ 2^{extent - i} ,{i, 0, extent}]
```

This reversal is due to an error made by European translators in the middle ages. Arabic numbers in Arabic writing appear as least significant digit first, i.e. Little Endian. For arithmetic this makes good sense because when adding numbers we start first with the least significant digit. However the Arabs also write from right to left. When European translators did not appreciate the details of performing arithmetic, so when they reversed the direction of writing letters, they did not reverse the direction of writing digits. Thus, Big Endian was invented in the 1300s, and it leaves mathematicians to do the reversal that the European translators neglected to do in 1300s.

2.2 Constants and Registers

Programmers conceptualize numeric constants in source code, and in processor registers, as having the rightmost bit as the MSB and leftmost bit being the LSB. I.e. as a Big Endian numbers.

Consequently, on Little Endian machines the bit a person envisions in memory starting with index zero at the left, appears in the register at the rightmost position, the LSB position.  This reversal being due to registers being conceptualized as Big Endian. It follows that on Big Endian machines the bit that comes from the leftmost of the bit array, appears at the leftmost of the register, at the MSB position. However,

So we have an interesting situation, Big Endian is mathematically flipped in blocks of bits, where the extent of the block must be known in order to perform the flip, while Little Endian is conceptually flipped due to how we conceptualize numbers as being written. Little wonder programmers find this confusing, and can sometime can be heard to say the situation is, "NUXI".

The problem with Big Endian is structural, but the problem with Little Endian is purely conceptual. Hence we could fix the Little Endian problem by conceptualizing numbers with their LSB at the leftmost. However, what starts as a conceptual problem becomes a computing problem when compilers do not provide such facilities. We can add a helper function until compilers mend their ways, if ever.

```
left_to_right( 0xC012 ) -->  0x4803
```

2.3 The impossibility of general conversion

Suppose we have two 32 bit words in memory that were written little endian.
```
a0 a1 b0 b1
```

Here `a0` is the least significant byte of the first word, and `b0` is the least significant byte of the second word.
We can then use the function `flip bytes` which reverses each byte pair. Applying that we get:

```
a1 a0 b1 b0
```

This is a fine conversion to Big Endian.  Now let us pass a 64 bit word to the same conversion function.

In little Endian:
```
d0 d1 d2 d3
```

Then converted:
```
d1 d0 d3 d2
```

This is missed up. The correct answer would be `d3 d2 d1 d0`.  What this example shows us is that to convert Little Endian to Big Endian requires knowing the program level type that is to be applied.  But given only the four bytes and the knowledge they were written on a little endian machine, we can not know which conversion algorithm to apply.  This same problem extrapolates to other scenarios and to conversion from Big Endian to Little Endian.


2. layer 0 format

  extent-literal:: (<control>+<tile>)*

The extent-literal models data as a bit array, with the zero index bit being leftmost, the array extending to the right. The index of the rightmost bit is called the array's 'extent'.  It follows that an array of 1 bit has an extent of 0.

When decoding an extent-literal the bit array is scanned from left to right, starting with the leftmost bit of the extent-literal.

Control codes are variable length and are scanned from left to right. The leftmost bit of a tile, when the tile interpreted as an Arabic Representation of a Natural Number, is the LSB of the title. In this way if the tile is expanded on the right, its leading bits in a left to right scan remain the same.

3. layer 1 format

  extent_literal:: <configuration><extension>*

  header:: ( <format> <display> ) <extent>

  format:: c_enum
  display: c_enum
  extent:  c_natural_number

  c_enum: ( tile* ) ; lynch summed
  c_natural_number ( tile *) ; lynch summed

Header is always DFS, 5 bit tile.

Example formats include, unspecified, ASCII, code point, UTF8

Extensions are first order tile lists.

  bits

  extent-literal version
  0-1  version number
  2    version extension follows: yes/no

  3    display selection follows / default

  payload

  4    big/little creation of contained data
  5    tile size follows
  6    format  selection follows / default

  7,8 Payload control

    00 tile array
    01 first order list
    10 DFS 
    11 BFS 

  9,10 payload alignment
     00 1  ; flows in bit stream
     01 8  ; byte aligned
     10 ?
     11 alignment follows
